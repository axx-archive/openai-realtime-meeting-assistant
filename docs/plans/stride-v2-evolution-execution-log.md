## How To Use This Log

1. Execute one wave at a time. Do not begin the next until this log marks the current wave `completed`.
2. After each wave, update: wave status, checklist, files changed, migrations applied, validation commands + outcomes, risks/blockers, and the prompt for the next wave.
3. **Compact previous waves** before writing the next-wave prompt (see Log Compaction).
4. Print the next-wave prompt in your final response so the user can continue in-session or paste it into a fresh session.

### Log Compaction

After completing a wave, compact ALL previously completed waves to:

    ## Wave N
    Status: `completed`
    Files: `file1` (created, N LOC), `file2` (modified, +a/-b)
    Risks carried forward: {only unresolved risks, or "none"}

Keep the CURRENT wave's section complete until the next wave starts. Future wave scaffolds hold only wave number, status, and scope checklist.

## Feed snappiness (hotfix)

Hotfix gen 249 (frontend performance dev, 2026-09-02). AJ: "clicking on conversations and posting stuff, it all still feels laggy"; "when sending a GIF in a chat, they are all stacked and you can't see them until you click"; "users should be able to send videos and photos". Measured on the sandbox with Playwright `performance.now()` marks (`$SP/perf-switch.mjs`: click a thread row → first message paint / settled = `data-projection-state="complete"` + 120 ms DOM quiet) against a seeded 100-message public channel (10 messages carry links, 4 carry GIFs; 80-message tail page). Chromium headless, 1440×900, 10–12 rounds per mode.

**Root causes (thread switch).** (1) Every index poll that carried a newer `updatedAt` for a thread the tab had already loaded DROPPED its messages (`mergeScoutChatIndexRows` → `messagesLoaded:false, messages:undefined`), so the next click on any busy channel showed the "Loading conversation" skeleton until the whole tail round-trip returned — on prod that round-trip is the 4.2 s. (2) `mountDesktopChatLinkPreview` fetched `/assistant/link-preview` for every linked message in the tail at mount (7 server-side page fetches per switch here). (3) The progressive head projection yielded a full animation frame (`rAF → setTimeout`) between every ≤12 ms chunk while assembling into a hidden stage. Read-marker POST (400 ms debounce, macrotask) and typing sync were already off the critical path; `setActiveTool` does no synchronous work of note.

**Fixes.** Index rows keep already-loaded messages as a STALE projection (`messagesStale:true`) → the click renders from memory instantly; `hydrateScoutChatThread` refetches stale rows, merges the tail via `mergeScoutChatMutationPage` (earlier pages survive) and reconciles by key (`scoutChatThreadProjectionKey`: thread id + every message id:render-hash + history seam) — an identical projection never rebuilds the feed. Rows prefetch their tail on `pointerenter`/`focus`; `scheduleScoutChatIdlePrefetch` warms the first four channel rows in `requestIdleCallback` (skipped under `saveData`). Link-preview metadata fetches wait until the card is within 800 px of the viewport (`deferDesktopChatCardFetch`, IntersectionObserver — fetches only, `<img>` stays eager). Head chunks continue on a macrotask.

Requests during a cold switch: before = tail + 7 × `link-preview` + 1 image; after = tail + blob images only (previews fetch as they scroll into view).

**GIF cards.** Root cause: the `.scout-chat-file--image` frame had no reserved size — until the (1.5 MB+) blob arrived the button was an 8 px sliver (desktop `min-height:0`), so a run of GIFs stacked as blank slivers; tapping opened the lightbox, which loaded the bytes, after which the card "dropped in". Server now stamps `width`/`height` on `/assistant/attachments` and `/assistant/giphy/import` responses (`attachmentImageDimensions`, GIF/PNG/JPEG/WebP header decode) and `sanitizeScoutChatFiles` bounds them on the record; the frame reserves `aspect-ratio: var(--media-aspect)` with a percentage-free width (a shrink-to-fit bubble resolves `%` against an unloaded `<img>` as 0 — that was the collapse) and a shimmer `is-loading` state; unsized legacy frames hold 160×120. GIFs animate on arrival; only under `prefers-reduced-motion` do they hold behind "GIF · tap to play". Pins: `TestIndexChatMediaAttachmentPins`, `TestIndexChatMediaAttachmentsRendered` (bytes held in flight → frames sized before load, no top shift after decode, RM hold + release).

**Photos + videos.** `attachmentUploadSafeMimes` += `video/mp4|quicktime|webm` (container check: ISO BMFF `ftyp` / EBML header; octet-stream declarations sniffed), both model allowlists unchanged (a video never reaches a model — its name/size/duration line does: `Attached file: clip.mov (quicktime, 9303 bytes, video 0:02).`), `blobInlineSafeMimes` += mp4/quicktime, `/artifacts/blob` serves `video/*` through `http.ServeContent` (206 byte ranges — Safari refuses `<video>` without them). Client: `scoutChatVideoUploadable`, 25 MB cap, local `<video preload=metadata>` probe for duration/frame size, inline `<video controls preload="metadata" playsinline>` card at the stored aspect (16:9 fallback) with a compact caption. Verified on the sandbox with mp4 / mov / webm clips (stored `width/height/duration`, card 420×318, `readyState 4`). Drive "Attach from Drive" (`assistantAttachmentFromFileHandler`) admits videos through the same allowlist.
